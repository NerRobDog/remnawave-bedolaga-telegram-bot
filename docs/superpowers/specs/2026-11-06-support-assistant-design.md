# Ассистент поддержки WatchDog — дизайн

Дата: 2026-11-06. Статус: черновик, ждёт ревью владельца.

## Зачем

Клиенты пишут в тикеты бота и кабинета. Чаще всего это «не работает» без подробностей: не сказано, какое устройство, приложение, сеть, когда перестало. Владелец тратит первый круг переписки на расспросы, потом сам лезет в панель и бота, чтобы понять, что с подпиской.

Владельцу важнее всего три вещи, в этом порядке:
1. Автопроверка аккаунта и подписки при каждом обращении.
2. Короткая сводка: что сломано и что сделать владельцу.
3. Список того, что ещё надо узнать у клиента. На голое «не работает» бот сам сразу задаёт клиенту недостающие вопросы.

Черновик ответа клиенту полезен, но вторичен. Его отправляет только владелец, своей кнопкой.

## Цели

- На каждый новый тикет в топик админов (ADMIN_NOTIFICATIONS_TICKET_TOPIC_ID, сейчас 18) приходит карточка разбора за десятки секунд.
- Карточка строится в первую очередь из детерминированных проверок (SQL и API, без LLM). LLM только связывает факты, называет вероятную причину и пишет черновик.
- Голое первое сообщение без деталей получает автоответ с вопросами из фиксированного набора, один раз на тикет.
- Ассистент никогда не мешает обычному потоку тикетов: если что-то упало, тикет живёт как раньше.

## Не цели

- Бот не отвечает клиенту свободным текстом LLM. Клиенту уходят только тексты из фиксированного набора вопросов либо черновик, который владелец сам отправил.
- Никаких действий с записью: ассистент не платит, не возвращает, не дарит дни, не перевыпускает ссылку, не сбрасывает устройства, ничего не удаляет и не синхронизирует. Он только говорит владельцу, что сделать.
- Это не чат-бот поддержки и не замена владельца.
- Не векторная база и не поиск по истории. Векторная база идёт отдельным проектом (своя сессия).

## Анти-цели (провал, даже если «работает»)

- Персональные данные клиента ушли в API.
- Клиент получил текст, который владелец не видел и не утверждал, кроме фиксированных вопросов.
- Тикет не дошёл до владельца или SLA-напоминание не сработало из-за ассистента.
- Карточка уверенно врёт: пишет «платёж зачислен» или «нода работает», когда в данных этого нет.

## Что уже проверено (spike, 2026-11-06)

Прототип в заметках сессии: `side-session-notes/local_1a6c31c3-…/support-spike/` (checks.py, scenarios.py, system_prompt.md, kb.json, report.md, grades.csv).

- Карта данных: 15 источников, 13+ автопроверок (`support-data-map.md` там же).
- checks.py на копии прод-БД с вычищенными персональными данными поймал все 15 подстроенных поломок (S01–S15).
- Чистая комната: 15 подстроенных + 14 реальных тикетов, слепая оценка, 232 балла максимум.
  Opus 5.5 — 231, 0 нарушений правил. Sonnet 5.5 — 220, 6 нарушений (в одном случае написал «платёж зачислен» без данных). Haiku 5.5 — 196, неверные гипотезы и неверно прочитанные факты.
- Ограничения замера: один оценщик той же семьи моделей, прогон субагентами, а не через API; у старых тикетов есть только события с отметкой времени.
- Реальный пример пользы: тикет #27 — проверка за 5 часов до обращения уже видела перевыпуск ссылки; на деле причину нашли через несколько дней.

## Решения владельца

1. Клиенты пишут в основном в тикеты (бот и кабинет). Поддержка в личке и в группах вне охвата.
2. Ассистент пишет черновик, отправляет владелец.
3. В API уходит: текст клиента как есть и факты подписки — тариф, срок, лимит устройств, модели устройств и ОС, состояние нод. Не уходит никогда: имя, @username, Telegram ID, e-mail, IP клиента, платёжные данные. Черновики и правки владельца хранятся в БД бота.
4. Главное — автопроверка, сводка действий и список вопросов клиенту.
5. Автовопросы: на голое «не работает» бот сразу сам задаёт клиенту недостающие вопросы.

## Устройство

### Поток

```
новый тикет (бот или кабинет)
  └─ как сейчас: запись в БД, уведомление админам          ← не трогаем
  └─ фоном, если флаг включён:
       1. checks   → факты + флаги (SQL/API, без LLM)
       2. auto-ask → если первое сообщение голое: вопросы клиенту (фикс. тексты), один раз
       3. card     → LLM по фактам + тексту + KB → структурный JSON
       4. render   → карточка в топик админов с кнопками
       5. store    → карточка, токены, стоимость, решение владельца
```

Шаги 1–5 запускаются фоновой задачей после того, как тикет сохранён и обычное уведомление ушло. Любая ошибка в них логируется и не всплывает в обработчик тикета.

Повторный запуск: новое сообщение клиента в открытом тикете пересчитывает проверки и карточку (не чаще раза в N минут на тикет; N — решение строителя, предлагаю 10).

### 1. Слой проверок

Чистая функция `collect(ticket) -> Facts` без LLM. Основа — `checks.py` из spike. Источники: БД бота (пользователь, подписка, тариф, транзакции, действия в кабинете из button_click_logs, ошибки бота, прошлые тикеты) и панель Remnawave (пользователь панели, устройства, запросы подписки, трафик, ноды сквада).

Флаги (код, важность, текст) — как в spike:
no_subscription, sub_expired, sub_expiring, daily_paused, desync_status, desync_expire, desync_devices, never_fetched, sub_history_unavailable, never_connected, offline_24h, device_limit_full, new_device_24h, revoked_recently, not_refetched_after_revoke, last_node_down, all_squad_nodes_down, some_squad_nodes_down, happ_base64, zero_traffic, traffic_flows, restricted, bot_errors, tx_pending, mass_tickets.

Уроки spike, которые обязательны:
- Панель хранит только последние 24 запроса подписки на пользователя. «Ни разу не забирал» — только если запросов ноль вообще; иначе флаг sub_history_unavailable.
- Ноды, выключенные админом, не считаются упавшими.
- desync_status не ставится, если подписка на посуточной паузе.
- Связь бот↔панель: subscriptions.remnawave_id = id пользователя панели.
- button_click_logs.user_id — это users.id бота, не telegram_id.

Каждая проверка в своём try: упала одна — в фактах пометка «нет данных», остальные идут.

Доступ к панели — **открытый вопрос, см. ниже**: API Remnawave или отдельная read-only роль в remnawave-db.

### 2. Автовопросы клиенту

- Срабатывают только на первое сообщение тикета и только один раз на тикет.
- «Голое» сообщение определяет детерминированное правило, не LLM: короткое и без деталей (устройство, приложение, сеть, время). Правило строится из фильтра кабинета `ticketQuality.ts` (MIN_TICKET_MESSAGE_LENGTH=120, MIN_TICKET_MESSAGE_WORDS=15, MIN_TICKET_DETAIL_WORDS=6, словарь жалоб), перенесённого в Python.
- Вопросы — закрытый набор с id и фиксированными текстами (устройство, приложение, когда перестало и что делали перед этим, мобильная сеть или Wi-Fi + оператор + регион, на всех устройствах или одном, какие сайты не открываются, скриншот ошибки). Тексты пишет владелец или утверждает мои.
- Какие вопросы задать, выбирается правилами по тексту и фактам: не спрашиваем то, что уже известно (например, модель устройства есть в панели — не спрашиваем устройство). Набор вопросов LLM не генерирует.
- Если проверки уже нашли поломку на нашей стороне (нода лежит, рассинхрон, подписка истекла), вопросы не задаём: это лишний круг для клиента.
- Тикет остаётся в статусе OPEN, чтобы SLA-напоминание владельцу работало. Автоответ помечается в истории тикета как сообщение системы, не владельца.
- Отправка в тот же канал, откуда пришёл тикет (бот или кабинет).

### 3. Карточка (LLM)

- Модель: `claude-opus-5-5`, adaptive thinking, effort по умолчанию. Официальный Python SDK `anthropic`.
- Ответ — структурный JSON через `output_config.format` (JSON Schema): facts[{icon, text}], cause, owner_action, ask_client[], draft. Рендер в текст карточки — наш код, не модель.
- Формат карточки:
  🔎 Разбор (✅ норма, ⚠️ отклонение, 🔴 поломка у нас, 🚨 действие клиента ломает доступ, ❓ нет данных; до 7 строк) / 💡 Вероятная причина / 🛠 Действие владельца / ❓ Спросить у клиента / ✏️ Черновик.
- Промпт и правила — `system_prompt.md` из spike: данные важнее слов клиента, не выдумывать причины, поломка нашей стороны важнее советов клиенту, тон на «вы», без извинений, сюсюканья и смайликов, без обещаний возвратов, дней и сроков, без внутренних названий (ноды, сквады, флаги).
- Prompt caching: системный промпт + KB — неизменный префикс с cache breakpoint; факты и текст клиента — после него.
- Отказ модели: `fallbacks: "default"` (бета server-side-fallback-2026-07-01). Таймаут, ошибка API, отказ, невалидный JSON → карточка только из флагов (шаг 4 без LLM-частей) с пометкой «разбор без модели».
- Стоимость: оценка ~3 цента на тикет (не замерено; замер — в теневой фазе).

### 4. Доставка и кнопки

- Карточка — ответом на уведомление о тикете в топике админов.
- Кнопки: [Отправить] — черновик уходит клиенту обычным путём ответа админа; [Править] — владелец присылает свой текст, уходит он; [Не надо] — ничего не уходит, карточка помечается.
- Отправка через существующие пути, без своего: бот — `notify_user_about_ticket_reply` (`app/handlers/admin/tickets.py`), кабинет — логика `reply_to_ticket` (`app/cabinet/routes/admin_tickets.py`). Запись сообщения в тикет, смена статуса и уведомление клиента идут как при ручном ответе.
- Кнопки доступны только админам и SUPPORT_MODERATOR_IDS; повторное нажатие после отправки ничего не шлёт (идемпотентно).

### 5. Хранение

Новая таблица (миграция Alembic) `support_assist_cards`: ticket_id, created_at, trigger (new_ticket / new_message), facts JSON (уже без персональных данных), flags, card JSON, model, tokens in/out/cache, cost, status (shown / sent / edited / dismissed / fallback), final_text (что ушло клиенту), auto_ask_sent (ids вопросов).

Правки владельца (draft → final_text) — материал для улучшения KB и промпта.

### Приватность

- В API уходит только то, что разрешил владелец (решение 3). Facts собираются сразу без запрещённых полей: id, telegram_id, username, имена, e-mail, IP, ссылки подписки, short_uuid, суммы и реквизиты платежей вместо фактов «есть незавершённый платёж».
- Текст клиента уходит как есть (решение 3). Если клиент сам написал в тексте e-mail или ID — уходит; владелец это разрешил.
- Тест: юнит-тест, что сериализованный payload к API не содержит ни одного поля из запрещённого списка, на синтетическом пользователе со всеми заполненными полями.

### База знаний

- Markdown в репозитории (`app/services/support_assist/kb.md`), записи короткие, по одной теме. Стартовая версия — 17 записей из spike `kb.json`, пишу я, вычитывает владелец.
- Меняется коммитом; изменение KB сбрасывает кэш промпта, это нормально.

### Включение

- `SUPPORT_ASSIST_ENABLED=false` по умолчанию. Отдельно `SUPPORT_ASSIST_AUTO_ASK_ENABLED=false`. Ключ — `ANTHROPIC_API_KEY` в env бота.
- Фазы:
  1. Тень: карточки приходят владельцу, кнопка [Отправить] скрыта, автовопросы выключены. 1–2 недели, замер стоимости и полезности.
  2. Кнопки отправки.
  3. Автовопросы.
- Выкат каждой фазы — по скиллу bedolaga-prod-update (бэкап, dry-run миграции, откат) и только после «да» владельца; выкаты координирует сессия «Пахан».

### Проверка качества (регрессия)

- Набор из spike: 15 подстроенных сценариев (scenarios.py клонирует тестового клиента и ломает его) + реальные тикеты.
- Проверки (без LLM) — обычные тесты: каждый сценарий даёт ожидаемые флаги.
- Карточки — eval-скрипт вручную перед сменой модели или промпта: прогон через API, оценка по ключам, сравнение с прошлым прогоном. Не в CI (стоит денег).

## Пробелы, которые не закрываем сейчас

- Анонимные платежи Tribute не попадают в БД бота (`app/handlers/balance/tribute.py`). Ассистент их не видит; в карточке — подсказка из KB «проверить Tribute вручную».
- Нет логов отдельных подключений — только последняя нода и трафик по дням.
- Тип сети и регион клиента знает только клиент — поэтому они в вопросах.
- Таблицы reachability пусты; когда заполнятся, это ещё одна проверка.
- Фильтр голых жалоб в кабинете (`ticketQuality.ts`, ветка `feat/support-reject-bare-complaint`, не выкачен) не даёт создать такой тикет в кабинете вовсе. Если его выкатят, автовопросы в кабинете почти не сработают — они нужны в первую очередь для бота. Конфликта нет, но правило «голого» сообщения должно быть одно и то же.
